## Decisions

| Decision   | Why   |
| ---------- | ----- |
| Porte `interfaces/fhir/` : un second `NinjaAPI` monté à `config/urls.py` `path("fhir/", …)`, rendu et parse `application/fhir+json` (et `application/json` accepté), handlers `DomainError` → `OperationOutcome` (`issue.code` : invalid_input→`invalid`, unauthenticated→`login`, forbidden→`forbidden`, not_found→`not-found`, conflict/no_room/no_clinician/has_dependents→`conflict`, invalid_transition→`business-rule`, rule_violation→`business-rule`, `details.code.coding` = le code produit, `details.text` = message, `expression` = champs, `diagnostics` = JSON des `details`) ; validation Ninja → `invalid_input` | §15.1 ; INSTALL.md « Ninja pour `/api/v1` et `/fhir` » |
| Un registre unique `interfaces/fhir/registry.py` déclare par ressource les interactions, paramètres de recherche, `_include` et `_sort` ; il sert à la fois `GET /fhir/metadata`, le refus des paramètres non déclarés (`invalid_input`) et le 405 `not-supported` des interactions non déclarées ; un test parcourt les routes Ninja et le registre dans les deux sens | Story CapabilityStatement « ne déclare rien qu'il ne serve pas, ne sert rien qu'il ne déclare pas » |
| Jetons d'API : identity `ApiTokenRecord(token_hash unique, user, label, expires_at)`, `hash_token` et `SecretsTokenGenerator` réutilisés ; `IssueApiToken.execute(*, user_email, label, days=90) -> str` (audit `identity.api_token_issued` `{user}`), `RevokeApiTokens.execute(*, user_email) -> int` (audit `identity.api_tokens_revoked` `{count}`), `AuthenticateToken.execute(*, token) -> Identity | None` (inconnu, expiré ou utilisateur inactif → `None`, donc un utilisateur désactivé perd aussitôt l'accès) ; commande `manage.py api_token <email> [--days N] [--revoke]` ; seed : un jeton fixe par rôle (`demo-admin-token`, `demo-clinician-token`, `demo-patient-token`, hachés, localhost seulement) | Story jeton ; question ouverte « désactivé, expire, révoque » |
| `SessionMiddleware` lit `Authorization: Bearer` sur tout chemin ; sous `/fhir` le cookie de session est ignoré, donc aucune surface CSRF : `/fhir/` est exempté de `SameOriginMiddleware` et de `DomainErrorPagesMiddleware` (Ninja `csrf=False` par défaut) ; l'`Identity` d'un jeton porte `session_expires_at` = expiration du jeton, `session_renewed=False` ; un utilisateur `must_change_password` reçoit 403 `forbidden` « Changez d'abord votre mot de passe. » comme l'écran le bloque | §15.4 ; `config/middleware.py:71`, `errors.py:29` ne connaissent que `/api/` ; `Identity` est taillé pour la session (`identity/application/ports/inbound.py:32`) |
| Lecture : contexte `drlibre.interop` (lectures et précondition `If-Match`, aucune règle métier), `SqlInteropQueries` lit les tables d'organisation, identity, scheduling, booking, notifications et audit ; chaque ligne porte `updated_at` ; la portée du lecteur `Reader(kind: anonymous|patient|clinician|admin, user_id, profile_id)` est résolue par `Readers.of(user_id)` (profil → praticien, rôle admin → admin, sinon patient) et appliquée dans le SQL ; pagination SQL avec total | light CQRS (architecture.md) ; aucune lecture actuelle ne porte `updated_at` ni la portée par acteur sur toutes ces ressources |
| `meta.versionId` = empreinte courte (12 hex de sha256) de l'état versionné : `updated_at` de l'enregistrement, et pour `PractitionerRole` aussi les ids et `updated_at` de ses plages et absences, pour `CodeSystem`/`ValueSet` ceux des spécialités ; ressources calculées (`Slot`) : empreinte de leurs champs ; `AuditEvent` : `"1"` ; `meta.lastUpdated` = le plus récent `updated_at` (ou `at`) ; `ETag: W/"<versionId>"` sur `read` | aucun compteur de version n'existe (`persistence/records.py`) ; une suppression d'absence doit changer la version de son `PractitionerRole` |
| `If-Match` : port `interop` `ConditionalWrites.run(target, expected, write)` ; l'adaptateur ouvre une transaction externe, verrouille dans l'ordre déjà pris par l'écriture visée (RDV : profil du praticien, patient, puis la ligne ; `Schedule` et `PractitionerRole` : profil puis la ligne, comme `lock_profile` ; utilisateur : sa ligne ; référentiel : l'ordre lu dans son use case, à vérifier en phase 9), recalcule la version, 412 si elle diffère, sinon exécute `write` dont l'unité de travail devient un savepoint ; sans `If-Match`, l'écriture part directement ; un test de course `transaction=True` par cible ; exception acceptée au passage par ports, comme `schedule_locks`, consignée dans architecture.md | §15.1 ; vérifier hors transaction laisserait passer une mise à jour perdue ; verrouiller la ligne d'abord ferait un interblocage avec l'ordre praticien, patient |
| Mise à jour (`PUT`) par diff : le mapper compare la ressource reçue à la ressource courante et traduit chaque changement autorisé en appel de use case ; un champ non modifiable changé → `invalid_input` avec le chemin FHIR en `expression` ; un champ réservé à un autre rôle (ex. praticien qui change autre chose que `notAvailable`) → `forbidden` ; `end`, `meta`, ids de participants calculés sont ignorés | Stories « sans pouvoir y changer autre chose » ; question ouverte « champ non autorisé » |
| Codes des cas ouverts : nommer un autre patient ou une salle en tant que patient → `forbidden` (comme `BookAppointmentAsCaller`) ; déplacement qui change de praticien ou de type → `invalid_input` sur `participant`/`serviceType` ; interaction non supportée → 405 `not-supported` (niveau HTTP, hors §4), vérifiée avant l'authentification ; interaction déclarée en écriture sans jeton → 401 ; `_count` > 100 → ramené à 100, `_count` < 1 ou non entier → `invalid_input` | question ouverte codes et `_count` |
| Champs publics : `Practitioner` = nom (`full_name` en `name.text`, `title` du profil en `name.prefix`), actif ; `PractitionerRole` = practitioner, organization (département), specialty, location (site et salle par défaut), healthcareService (types actifs réservables en ligne), `availableTime`, `notAvailable` sans motif, bio en extension ; personnel en plus : email, téléphone, poids round robin, motif des absences, types non réservables en ligne, praticiens inactifs ; admin seul : `Practitioner` admins avec un `PractitionerRole` d'id = l'id utilisateur codé `admin` | §15.2 ; question ouverte champs publics : ce que montre la page publique du praticien |
| Hôpital : `Organization` type `prov` (nom, code en `identifier`, adresse, téléphone, fuseau et position en extensions) est la ressource écrite ; la `Location` du site garde le même id et se lit seulement (adresse, téléphone, `position`, fuseau) ; `Location` en écriture = les salles ; département = `Organization` `dept` `partOf` l'hôpital (pas de champ actif : actif si son hôpital l'est) | question ouverte « une ou deux requêtes » : une seule écriture, une seule source de vérité |
| Spécialités : chaque spécialité est un `CodeSystem` (id = id produit, un concept code/nom, `status` `active`/`retired`) que l'admin crée, modifie et supprime (`SaveSpecialty`, `DeleteSpecialty` avec `has_dependents`) ; le `ValueSet` d'id `specialties` réunit les `CodeSystem` actifs et se lit seulement : l'écrire doublerait la source de vérité, écart à la puce « admin … `ValueSet` » signalé dans la PR et `open-questions.md` | §15.2, §15.4 ; un seul chemin d'écriture par concept |
| `Practitioner` et `Patient` créés par l'admin passent par `SaveUser` ; le mot de passe temporaire exigé par `SaveUser` arrive dans l'extension write-only `temporary-password`, jamais renvoyée ni journalisée | question ouverte mot de passe ; même règle que la console |
| `Slot` : id = base32 minuscule sans padding de (profil 16 o, type 16 o, début en minutes epoch 4 o), décodable, donc stable pour même praticien, type, début ; `Slot.schedule` = la plage (`Schedule`) qui couvre le début ; scheduling `FindSlotStates.execute(*, appointment_type_id, clinician_id: Id | None, start, end, statuses) -> tuple[SlotState(clinician_id, rule_id, start, end, status)]` ; `free` vient de la même requête que `FindFreeSlots` sur `scheduling_slot` (qui porte `clinician_id`), en une lecture pour tous les praticiens du département quand aucun n'est nommé ; seuls les autres états recalculent par praticien et marque `busy` (RDV actif), `busy-tentative` (retenue), `busy-unavailable` (absence) ; autres statuts que `free` pour le personnel seulement (`forbidden` sinon) | §15.6 ids stables ; `FindFreeSlots` ne rend pas le praticien de chaque créneau (`domain/slot.py`) |
| `Schedule` = une plage (`AvailabilityRule`) : acteurs `Practitioner` et `Location` salle, `planningHorizon` = `valid_from`/`valid_to` en lecture seule (un client ne le fixe pas, comme l'écran), extension `availability` (jour, début, fin, pas) ; écritures par `SaveAvailabilityRule`/`DeleteAvailabilityRule`, qui refusent déjà l'admin et un autre praticien | question ouverte `planningHorizon` ; `ClinicianWrites` |
| Absences : `PUT PractitionerRole/<id>` par son praticien, diff de `notAvailable` → `RecordTimeOff`/`DeleteTimeOff` dans une transaction (tout ou rien) ; `description` = motif | §15.2 |
| `Appointment` regroupe trois sources sous un seul type : RDV (id du RDV), entrée d'attente non réservée (id de l'entrée), retenue (id de la retenue, `pending`, personnel seul : praticien pour son agenda, admin) ; une entrée `BOOKED` n'est plus servie, son RDV l'est | §15.2, §15.3 |
| « Une seule ressource » : `AcceptWaitlistOffer` place le RDV avec l'id de l'entrée (`Appointment.book(id=…)`, `Placement.place(appointment_id=…)` facultatifs) ; `Appointment/<id-entrée>` passe de `proposed` à `booked` ; `AppointmentResponse` = une entrée `BOOKED` (même id, `appointment` → `Appointment/<id>`, acteur le patient, `accepted`, version de l'entrée), lue sans passer par l'audit | §15.3 ; aujourd'hui le lien n'existe que dans l'audit `booking.waitlist_accepted` |
| Réservation FHIR = `BookAppointmentAsCaller` (patient, praticien, admin, round robin sans praticien) ; `slot` décodé en praticien, type, début ; `reasonCode` refusé à la création (`invalid_input`) car aucun écran connecté ne le saisit | Story réserve ; « aucune écriture FHIR ne fait ce que l'API refuserait » |
| Notes cliniques : `Appointment.comment` lu et écrit (`WriteClinicalNotes`) par le praticien du RDV seul | question ouverte notes : l'écran le permet |
| Hors FHIR : offre manuelle de l'admin (pas d'interaction §15.4) ; le praticien ne voit pas les entrées qui le désignent (§15.4 : son agenda seulement) | questions ouvertes offre manuelle, praticien préféré |
| `AuditEvent` : `action` C/U/D d'après le suffixe `.created/.updated/.deleted`, E sinon ; `subtype` = action produit ; `agent.who` = `Practitioner`/`Patient` de l'acteur ; `entity.what` = la ressource FHIR quand le type est servi, sinon `identifier` `<type>/<id>` ; métadonnées en `entity.detail` ; correlation id en extension ; recherche `action` sur C/R/U/D/E, `entity-type` sur le type produit | §15.2 ; codes R4 de `AuditEvent.action` |
| `Communication` : `category` = `kind`, `topic.text` = titre, `payload.contentString` = corps, `sent` = `created_at`, `received` = `read_at` ; seul `received` vide → valeur est modifiable (`MarkNotificationRead`) | Story notifications |
| `_sort` déclaré : `name` (Organization, Location, HealthcareService, Practitioner, Patient), `date` (Appointment, AuditEvent), `start` (Slot), `sent` (Communication), `-` pour décroissant ; tri par défaut stable (id en dernier) | §15.1 |
| Preuve de performance : un scénario Locust « recherche `Slot` FHIR » ajouté à `loadtests/locustfile.py` et un run `./scripts/load-run.sh` en fin de plan, résultats dans `load-results.md` | contrainte p95 < 200 ms, recherche comprise |
